# Аудит похожих скиллов на skills.sh

Дата проверки: 2 августа 2026 года.

## Итог

Полного аналога VibeCode Control на skills.sh не найдено. Решение: **KEEP** — сохранить текущий скилл, не заменять его и не подключать найденные workflow-скиллы целиком.

Ближайшие кандидаты закрывают отдельные участки процесса, но не весь контур:

```text
inspect/adopt → граф ролей и исполнителей → фоновые агенты → quality gates
→ review/merge → doctor/scheme check → управление зависимыми скиллами
```

## Методика

Проверялось содержимое `SKILL.md`, а не только название, число установок или автоматический бейдж аудита. Прямым аналогом считалось только решение, которое одновременно покрывает:

- подключение нового и legacy-репозитория;
- исполняемую конфигурацию и граф состояний;
- роли, фактических агентов, модели, effort и права;
- доставку скиллов фоновым Claude и Codex;
- объективные quality gates и доказательства, привязанные к Git SHA;
- review, merge gate и диагностику остановок;
- обновление, проверку целостности и замену зависимых скиллов.

## Отклонённые по безопасности варианты

- [applecg/devflow](https://skills.sh/applecg/devflow/devflow): содержит сценарии с `git reset --hard` и широким staging. Для фонового процесса это неприемлемо без более сильных внешних ограничений.
- [dnzengou/flowforge](https://skills.sh/dnzengou/flowforge/devflow): предусматривает широкие Git-операции и push/deploy без достаточного внешнего гейта.
- Один найденный источник был недоступен для чтения. Он признан непроверяемым и исключён из рекомендаций.

Автоматический аудит skills.sh и популярность кандидата использовались только как сигналы. Они не заменяют чтение содержимого, проверку происхождения и анализ фактических команд.

## Рекомендации по узлам графа

| Узлы | Решение | Обоснование |
|---|---|---|
| `inspect`, `skill_preflight`, `quality_gates`, `merge_gate` | `zero-skill` | Надёжнее использовать VibeCode Control, детерминированные скрипты, CI и GitHub rulesets |
| `prepare_issue` | Пока `zero-skill` | `brainstorming` или `writing-plans` стоит проверять только при фактическом падении качества постановок |
| `tdd_red`, `implement` | Стековый скилл при доказанном пробеле | Общий workflow-скилл дублирует управляющий контур; выбирать нужно под конкретный стек и версию |
| `final_review` | Независимый review/security-скилл только после сравнения | Нельзя автоматически назначать ревьюеру тот же скилл, что и исполнителю |

## Что стоит добавить в следующую версию

1. Постоянный `scenarios.yml`: требование → нормальный, граничный и ошибочный сценарий → конкретный тест.
2. Явный шаг фальсификации готовности: попытаться опровергнуть результат, а не только подтвердить прохождение проверок.
3. Адаптер поиска через официальный `skills` CLI. Публичный API skills.sh требует OIDC-аутентификацию; CLI подходит лучше для ограниченного воспроизводимого поиска. См. [документацию API skills.sh](https://skills.sh/docs/api).

## Ограничения аудита

Это статический аудит содержимого. Сравнительные запуски кандидатов на одном проекте с одинаковыми моделью, effort, правами, кодом и тестовыми сценариями не проводились. Поэтому ни один кандидат не объявлен эмпирически лучше или хуже по качеству результата.

Финальное решение: **KEEP VibeCode Control**, сторонние аналоги не подключать; три улучшения выше рассматривать как отдельные изменения после сценарных тестов.
